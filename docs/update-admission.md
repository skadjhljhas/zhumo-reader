# 读者与更新的准入门禁：内部候选25

本轮将门禁接入实际阅读器启动：在Electron ready、单实例转发和任何配置写入初始化之前，同步调用admitReader。保护范围包括该用户资料目录，以及打包程序的实际目录。多个资料目录使用同一程序时，程序目录门禁也会阻止它们启动。

协调数据默认存放在用户AppData中的ZhuMo-update-coordination，与被保护资料分开。显式ZHUMO_UPDATE_COORDINATION用于协调者及隔离验证；读者和更新进程必须使用同一个协调根。测试运行器默认使用work下按测试profile区分的独立目录，跨进程门禁测试显式共享自己的临时协调目录，不污染真实用户资料。

## 双向确认

读者先确认没有更新声明，发布自己的唯一登记，再检查一次更新声明，只有第二次检查通过才进入应用。更新则先发布自己的声明，再检查竞争更新与所有读者。发布采用先完整写入、同步，再以唯一名称原子发布的方式。并发竞争可以使双方退让，但不会让读者和更新同时获准操作共享范围。

读者登记按进程生命周期保留，不在某个窗口关闭或before-quit时提前撤销。更新看到进程真正结束后才能移除过期登记，避免漏掉退出阶段的配置刷新。Windows记录并核对进程创建时间，避免单凭复用的PID判断旧进程还活着；身份不可查询时保守地视为仍存活。

所有保护范围共用该事务的一份原子阶段记录。不能逐个解锁目录，否则完成记录写到一半时可能已有读者进入。开始实际写入前，markMutating必须成功发布；之后cancel不能解除门禁。complete先运行提交/恢复验证，成功发布唯一完成记录后才允许读者进入；后续只剩协调文件清理。

## 崩溃与恢复

preparing阶段的所有者已结束，且尚未声明原文件改动时，过期声明可以移除。mutating阶段的所有者消失后，门禁继续保留。新协调者需要明确的恢复token、完全相同的保护范围及一致的事务位置才能接管；仍然活着的旧所有者不能被抢占。

恢复旧声明时，新声明先覆盖相同范围，直到验证结束。旧声明被标记完成时，新门禁仍阻止读者；新声明也完成后才解除。阶段记录损坏、缺失或无法核对会阻止进入，不用“进程不见了”推断磁盘数据一定完整。

因门禁受阻的阅读器在初始化资料前退出，普通启动说明需要等待更新或先恢复；后台验证不弹对话框。事务路径只是协调数据，本模块不会把它当脚本执行，也不自动信任其中的恢复指令。

## 验证

- 单元覆盖共享范围、无关范围、取消、验证失败保留门禁、多个范围共用原子完成状态、完成记录无法覆盖时仍阻止所有范围、PID复用与无法查询时的保守行为、拒绝接管活跃所有者。
- 真实候选25：更新门禁存在时启动返回73，既有profile文件不增不改；活跃读者阻止更新；同一程序的门禁也保护另一profile；准备阶段崩溃后可正常阅读；写入阶段崩溃后继续阻止启动，显式恢复并验证后重开，原字号23恢复。
- 四轮、每轮六个独立Node进程同时竞争，加入有限随机退让，要求确实有人获准进入且拒绝仅来自竞争原因。已观察到更新获准和读者获准两种结果，没有同轮双方获准。它是实际竞争检验，不代替对所有调度的证明。
- 二次启动仍可通过现有单实例机制打开另一个隐藏阅读窗口；关掉其中一个窗口，更新仍被活着的主进程拒绝。

测试中一个旧断言过早悬停了重开前的Reader节点，改为等待旧节点离开后再检查；另一个多窗口断言错误依赖窗口数组顺序，改为按目标Page定位窗口。没有改变产品来迁就这两个断言。

## 仍未完成的更新范围

这套门禁只覆盖参与协议的新版读者和显式使用准入API的协调者。旧版读者、旧卸载器及不合作的外部编辑器不受文件声明自动约束。不要把短命的capture helper结束前持有门禁，冒充整个安装期间都持有门禁。

正式协调者还必须把正常关闭、原版兼容保护、快照、文件替换/原子版本切换、配置迁移、恢复与验证串成完整事务。可继续研究由独立帮助进程在整个操作期间持有旧版已使用的Electron单实例锁，但要验证它对资料、启动转发和退出刷新的影响，不能假定“无窗口”就完全不写profile。当前未启用正式自动更新/安装入口，完整目标保持未完成。
