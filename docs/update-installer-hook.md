# 旧卸载之前的保护入口：候选22工程记录

`src/main/update-helper.ts` 是独立构建入口，输出 `out/main/update-helper.js`，随桌面包一起保存。用新版本已暂存的Electron可执行文件以Node模式运行，不加载阅读器入口、不创建窗口、不打开用户模型或发出模型请求。帮助程序必须位于旧程序/配置之外。

调用约定为 `ELECTRON_RUN_AS_NODE=1 <新运行时> <帮助脚本> --plan <绝对计划路径> --installation-root <本次实际卸载目录>`。帮助程序把实际卸载目录与计划中的程序根进行canonical精确核对，拒绝保存甲目录却卸载乙目录。每次使用新的计划文件与输出目录，不复用已经留下结果文件的旧计划。计划结构：

```json
{
  "version": 1,
  "action": "capture",
  "sources": ["C:\\旧朱墨", "C:\\旧配置"],
  "programRoots": ["C:\\旧朱墨"],
  "destination": "C:\\升级保存点\\本次唯一目录"
}
```

`sources` 要完整覆盖需要保护的程序、配置与文稿根；Junction目标由保存模块纳入。`programRoots` 必须属于保存范围。计划和结果不能位于源目录之内。帮助程序不推断实际注册表位置、不盲目选择某个用户profile，这些仍是发行安装器协调层的责任。

进程检查使用隐藏PowerShell查询本机Win32_Process，只读进程名、PID和可执行路径，不读取命令行。UTF-8输出保证中文路径不会被错误解码。旧程序目录中有进程、相关进程的位置不可读、查询失败或超时都拒绝继续；不会强杀阅读器。保存每个根后再次检查，完成后重新校验保存点。`<计划路径>.result.json` 使用独占创建并同步写入，失败不会留下成功报告；退出码非零。

## NSIS钩子

`build/update-preservation.nsh` 提供 `ZhuMoCaptureBeforeUninstall`。它临时设置并恢复当前安装进程的Node模式环境变量，同步等待帮助程序；启动或保存失败直接中止当前安装Section，后面的卸载不执行。

应在旧卸载调用之前使用，不能放进electron-builder的 `customInstall`：该宏在默认模板的旧卸载之后才运行。当前宏已在隔离的NSIS脚本中实际编译与执行，**尚未配置进正式发行安装器**。

## 实际验证与边界

`tests/e2e/update-installer.spec.ts` 使用候选22包内的帮助入口、真正编译的NSIS安装/卸载程序、临时目录，不注册应用、不创建快捷方式、不触及本机已有朱墨安装。

| 场景 | 已检查结果 |
| --- | --- |
| 完整保存 | 报告成功、清单可核验之后，NSIS卸载器才写入启动证据并删除临时旧目录；随后从保存点恢复MD的BOM/CRLF和未知资源原字节 |
| 来源失联 | 安装返回43，卸载器未启动，旧文稿仍在 |
| 旧目录存在运行中的程序 | 真实隐藏Writer.exe被查出；安装返回43，Writer仍然存活，卸载器未启动 |
| 保存中另一写入者改动原稿 | 保存失败、安装返回43，卸载器未启动，最新改动仍留在原目录 |
| 计划误选了另一个安装目录 | 与安装器实际卸载目录不一致，保存与卸载均不执行，目标原稿保留 |

原配置目录在五种场景中均保留。这个证据比单纯Node模拟删除多验证了NSIS执行顺序，但不是已发布旧版完整安装器→正式新版的最终验收。当前卸载器是隔离fixture，使用真正NSIS的递归删除，不含历史注册表/文件关联/快捷方式配置。

进程清单是检查时刻的事实，**不是整个更新期间的独占锁**。正式接入还必须解决：检查后重新启动的竞争；正常关闭与写入停止；所有可能使用目标profile的程序范围；新运行时的可信暂存；旧/新程序拥有文件清单与冲突；正式profile身份、完整设置和文稿路径迁移；失败后的自动恢复/回滚。不能仅凭宏返回成功就宣称这些问题已解决。

候选22是增加后台入口的工程构建，没有打开正式安装升级入口。上一用户阅读保存点候选21继续保留。
